## 1. 适配背景

本项目为 AI 辅助快速构建（vibe coding）的 Flask 3 + PostgreSQL 14 演示系统，当前仅按**本地单机演示态**设计：

- 使用 Flask 内置开发服务器（werkzeug）单进程运行，监听 `127.0.0.1:8000`；
- 数据库连接串、JWT 密钥以**代码默认值**形式硬编码（含明文密码 `Langchain2026`）；
- 五类定时预警/到期揭示/超时失效任务以**进程内 daemon 线程**运行；
- 启动即自动建表并写入**演示种子数据**（6 账号/5 企业/4 订单）；
- Docker Compose 将 PostgreSQL 5432 端口暴露在 `0.0.0.0`；
- 依赖清单使用 `>=` 浮动版本，且测试依赖（pytest/requests）混入运行时依赖。

以上各项在本地演示场景无害，但直接部署到服务器将产生**凭据泄露、越权访问、任务重复执行、并发能力不足**四类生产事故风险，须按本方案完成适配后方可上线。

**当前架构中已满足生产要求的项（无需修改，避免过度改造）**：

| 项 | 现状 | 位置 |
|---|---|---|
| debug 模式 | 已关闭（`debug=False`） | run.py:24 |
| 统一错误拦截 | 500 返回"服务内部错误"，不泄露堆栈 | backend/__init__.py:77-80 |
| 请求体上限 | `MAX_CONTENT_LENGTH = 21MB` | backend/__init__.py:41 |
| 文件上传防护 | 扩展名白名单 + 20MB 上限 + uuid 随机文件名 | backend/api/files.py:17-34 |
| 密码存储 | bcrypt（rounds=10） | backend/security.py:30-32 |
| JWT | HS256 + 8h exp + 签名常量时间比较 | backend/security.py:52-74 |
| SQL 注入 | 全部参数化查询（psycopg 占位符） | 全部 API 模块 |
| 前端接口地址 | 相对路径 `/api/v1`，无硬编码 host | frontend/js/api.js |
| 时区适配 | 会话级时区机制（MINE_PG_TZ）已具备 | backend/db.py:15 |

## 2. 目标服务器环境参数（基线假设）

> 以下为方案默认基线。若实际服务器与基线不符，仅需替换 §4 中对应步骤的参数值，方案结构不变。

| 类别 | 参数 | 基线值 |
|---|---|---|
| 操作系统 | 发行版 | Ubuntu Server 22.04 LTS（x86_64） |
| 硬件 | CPU/内存/磁盘 | 2C / 4GB / 40GB（含 uploads 独立预留 10GB） |
| 运行时 | Python | 3.14.x（与本地开发环境 3.14.6 对齐，最低 3.12） |
| 数据库 | PostgreSQL | 14（独立容器或主机安装，仅监听本机/内网） |
| 反向代理 | Web 服务器 | Nginx 1.22+，域名 + HTTPS（Let's Encrypt） |
| 应用服务器 | WSGI | waitress（纯 Python，Windows/Linux 通用，无 C 编译依赖） |
| 进程守护 | init | systemd（app.service + app-jobs.service 两个单元） |
| 防火墙 | 对外端口 | 仅 80/443；5432、8000 一律不对公网 |
| 部署账号 | 系统用户 | `mine`（非 root，专用于运行本服务） |
| 部署路径 | 代码/数据 | `/opt/mine-platform`（代码）、`/data/mine/uploads`（上传件） |
| 业务时区 | 时区 | Asia/Shanghai（服务器 `timedatectl` + `MINE_PG_TZ` 双侧确认） |

## 3. 架构调整范围

**当前架构（本地演示态）：**

```
浏览器 ──> Flask dev server (127.0.0.1:8000, 单进程)
                │  进程内 daemon 线程：定时任务
                │  每请求新建 PG 连接
                └──> PostgreSQL 14 (Docker, 0.0.0.0:5432)
```

**目标架构（服务器生产态）：**

```
浏览器 ──HTTPS──> Nginx (443, TLS 终结, 静态资源+uploads 长缓存, 反代)
                      │  proxy_pass http://127.0.0.1:8000
                      ▼
              waitress 多线程 (127.0.0.1:8000, systemd: app.service)
                      │  【无定时任务】MINE_DISABLE_JOBS=1
                      ▼
              PostgreSQL 14 (容器/本机, 仅 127.0.0.1:5432)

              独立任务进程 (systemd: app-jobs.timer, 每 MINE_JOBS_INTERVAL 执行一轮)
                      └──> 同一 PostgreSQL
```

**调整范围清单（全部为环境适配，非业务变更）：**

| 范围 | 调整内容 | 涉及文件 |
|---|---|---|
| 入口服务器 | werkzeug → waitress，监听地址 127.0.0.1（由 Nginx 对外） | run.py、requirements.txt |
| 密钥注入 | DSN/JWT 密钥去掉代码默认值，强制环境变量 | backend/db.py、backend/security.py |
| 任务拆分 | Web 进程禁用任务线程；新增独立任务执行入口 | run.py 新增 `--jobs` 模式、部署 systemd 单元 |
| 连接池化 | 每请求新建连接 → 进程级连接池（q1/qall/execute 接口不变） | backend/__init__.py、backend/db.py |
| 匿名直链收紧 | 删除匿名 `/uploads/<name>` 直链，统一走已鉴权的 `/api/v1/files/<file_id>` | backend/__init__.py |
| 登录防护 | 登录接口增加 IP+账号滑动窗口限流（不改登录成功/失败业务语义） | backend/api/auth.py |
| 种子数据开关 | 演示数据写入增加显式开关，生产默认不写 | run.py、backend/seed.py |
| 上传目录外置 | UPLOAD_DIR 支持 `MINE_UPLOAD_DIR` 覆盖（默认值不变，零破坏） | backend/__init__.py |
| 健康检查 | 新增 `GET /api/v1/health`（SELECT 1 探活） | backend/api/__init__.py |
| 依赖锁定 | 精确版本锁定；pytest/requests 移出运行时依赖 | requirements.txt |
| 数据库端口 | 5432 仅绑定 127.0.0.1；密码改环境变量注入 | docker-compose.yml |
| 反向代理/TLS | 新增 Nginx 配置、HTTPS 证书、HTTP→HTTPS 跳转 | 服务器侧新增配置文件 |

**明确不在本次范围内（避免业务变更）**：JWT 吊销机制、角色权限矩阵调整、上传文件魔数校验、CORS 配置（同源部署不需要）、承运商端恢复等 —— 记入 §6 风险跟踪与后续迭代。

## 5. 部署前必须修复的代码问题清单

> 优先级定义：**P0**=不修复则禁止上线（安全/数据风险）；**P1**=上线前应修复（高概率生产事故）；**P2**=上线后尽快（性能/运维便利）。
> 每项修复方式均不触碰业务流程代码（状态机、审批流、价格计算等零改动）。

### C1 开发服务器用于生产

| 项 | 内容 |
|---|---|
| 问题位置 | run.py:24（`app.run(host='127.0.0.1', port=port, debug=False)`） |
| 问题描述 | 使用 Flask/Werkzeug 内置开发服务器，单线程处理请求，官方明确声明不适用于生产 |
| 影响范围 | 全部接口；并发>1 即排队，慢请求（导出/上传）会阻塞全站；无超时保护 |
| 修复优先级 | P0 |
| 具体修复方式 | ① requirements 新增 `waitress`；② run.py 改为 `from waitress import serve; serve(app, host='127.0.0.1', port=port, threads=8)`（保持 127.0.0.1，由 Nginx 对外）；③ run.py 增加 `--jobs` 参数分支：传入时仅执行建表+任务循环不启动 Web（供 systemd 任务单元调用） |
| 验证标准 | 本地 `python run.py` 正常服务；`ab -n 2000 -c 50` 压测 0 错误；186 项回归全 PASS |

### C2 数据库连接串硬编码（含明文密码）

| 项 | 内容 |
|---|---|
| 问题位置 | backend/db.py:9（`DEFAULT_DSN = 'postgresql://postgres:Langchain2026@…'`） |
| 问题描述 | 生产凭据以代码默认值存在，且已随 Git 仓库提交（README 亦明文展示），任何拿到代码者即获库凭据 |
| 影响范围 | 数据库完全失控风险（拖库/篡改）；违反凭据管理基本要求 |
| 修复优先级 | P0 |
| 具体修复方式 | ① 删除 DEFAULT_DSN 默认值，`dsn()` 改为：未设置 `MINE_PG_DSN` 时 `raise RuntimeError('MINE_PG_DSN 未设置…')`（启动即失败，杜绝静默用默认库）；② Git 历史中的密码视为已泄露：生产库使用全新强密码；③ 本地开发通过 `.env`/启动脚本注入（提供 `.env.example` 模板，不含真实值） |
| 验证标准 | 未设 MINE_PG_DSN 时 `python run.py` 立即报错退出；设置后全量回归 186/186 PASS；全仓库 grep `Langchain2026` 无代码命中 |

### C3 JWT 密钥硬编码默认值

| 项 | 内容 |
|---|---|
| 问题位置 | backend/security.py:21（`JWT_SECRET = os.environ.get('MINE_JWT_SECRET', 'mine-platform-demo-secret-2026')`） |
| 问题描述 | 密钥随代码公开，攻击者可离线签发任意 uid/roles（含 PLAT_ADMIN）的合法 token，完全绕过登录 |

### C4 定时任务随 Web 进程多实例重复执行

| 项 | 内容 |
|---|---|
| 问题位置 | backend/__init__.py:105-108（daemon 线程启动 jobs.run_loop） |
| 问题描述 | 任务与 Web 同进程。waitress 单进程下勉强可用，但只要扩到多进程/多实例（或误配 gunicorn 多 worker），五类预警扫描、到期自动揭示、超时订单失效将**每个进程各跑一份**，产生重复预警/重复状态流转 |
| 影响范围 | 预警重复通知、揭示/失效重复执行（含归集锁定量回退类写操作，重复执行有数据一致性风险） |
| 修复优先级 | P0 |
| 具体修复方式 | ① 部署侧 Web 进程统一 `MINE_DISABLE_JOBS=1`（机制已存在，零代码）；② 新增独立执行入口（run.py `--jobs` 分支，复用 jobs.run_loop 单轮执行后退出），由 systemd timer 每小时调度——单实例调度天然无并发重复 |
| 验证标准 | app.service 进程内无线程 `mine-jobs`（`/proc` 或线程名检查）；app-jobs.timer 触发日志单轮执行；连续两轮触发间预警表无重复记录 |

### C5 数据库连接无池化

| 项 | 内容 |
|---|---|
| 问题位置 | backend/__init__.py:45-48（`@app.before_request` 内每请求 `psycopg.connect(...)`）、backend/db.py:31 |
| 问题描述 | 每个请求新建+销毁一条物理连接（TCP+auth+会话时区设置），并发上升时连接建立延迟放大、PG 侧连接数抖动 |
| 影响范围 | 接口响应时间随并发恶化；PG `max_connections` 压力 |
| 修复优先级 | P1 |
| 具体修复方式 | 引入 `psycopg_pool.ConnectionPool`（psycopg 官方池，新增依赖 `psycopg[pool]`）：进程启动建池（min=2, max=10, timeout=30，连接 kwargs 含会话时区 options），before_request 从池 `getconn`、teardown `putconn`（commit/rollback 逻辑原样保留）；`with_db()` 同步改池；**q1/qall/execute 及全部 SQL 不动** |
| 验证标准 | 全量回归 186/186 PASS；压测期间 PG `pg_stat_activity` 连接数稳定在池上限内；接口 P95 延迟不高于改造前 |

### C6 附件匿名直链暴露

| 项 | 内容 |
|---|---|
| 问题位置 | backend/__init__.py:100-102（`GET /uploads/<filename>` 无任何鉴权） |
| 问题描述 | 服务器上 uploads 目录内所有文件可被未登录者直接 URL 访问；`sys_file` 中的营业执照、报价附件等业务文件经此路径泄露 |
| 影响范围 | 企业证照/业务附件未授权访问（合规风险） |
| 修复优先级 | P1 |
| 具体修复方式 | 删除 `_uploads` 直链路由；附件访问统一走已鉴权的 `GET /api/v1/files/<file_id>`（files.py:49 已有登录校验+按 fileId 查库，能力收敛）。前端已确认无任何 `/uploads/` 引用（frontend 全目录 grep 零命中），删除无前端影响 |
| 验证标准 | 未登录 `GET /uploads/<任一文件>` 返回 404；登录后经 `/api/v1/files/<file_id>` 下载正常；UI 回归（含报价附件上传下载）通过 |

### C7 登录接口无防爆破限流

| 项 | 内容 |
|---|---|
| 问题位置 | backend/api/auth.py:108-128（`POST /api/v1/auth/login`） |
| 问题描述 | 无频控，可无限次尝试口令（demo 账号弱密码组合易被猜中）；线上暴露后必然被扫描 |
| 影响范围 | 口令爆破 → 账号接管 → 以合法身份越权操作 |
| 修复优先级 | P1 |
| 具体修复方式 | auth.py 登录函数入口增加进程内滑动窗口计数（key=客户端IP+username，60 秒内 5 次失败则该组合锁定 10 分钟，返回 40001「尝试过于频繁」）；成功登录清零计数。不改登录成功/失败的业务语义与返回契约（仅新增一种 40001 场景） |

## 7. 回滚预案

**原则：代码回滚 + 环境回滚双层，均在 5 分钟内可执行。**

1. **应用回滚（最常用）**
   - 保留上一版本完整目录 `/opt/mine-platform/app@previous`（每次发布前 `cp -al` 硬链接快照，或 git tag）；
   - 回滚动作：`sudo systemctl stop app && sudo -u mine cp -a /opt/mine-platform/app@previous/. /opt/mine-platform/app/ && sudo systemctl start app`；
   - 验证：`/api/v1/health` 200 + 首页 200。
2. **数据库回滚（本次适配不涉及 schema 变更）**
   - 本次全部改动**不含任何 DDL/迁移**（init_schema 与现版本一致），不存在 schema 回滚需求；
   - 数据级回滚仅用于误操作场景：恢复最近一次 `pg_dump`（部署脚本中固定每日 02:00 全量备份 + WAL 归档可选）；
   - 附件回滚：`rsync -a /data/mine/uploads@snapshot/ /data/mine/uploads/`。
3. **环境配置回滚**
   - env 文件与 systemd/Nginx 配置纳入 `/opt/mine-platform/deploy/` 目录并 git 管理（不含真实密钥，密钥项以占位符+文档说明）；
   - 配置回滚 = 恢复上一版配置文件 + `systemctl daemon-reload && systemctl restart app nginx`。
4. **回滚决策标准**
   - 部署后验证清单任一 P0 级项（服务拉起/健康检查/登录/核心链路）不通过 → 立即回滚；
   - P1/P2 项问题 → 评估后可带问题观察，24h 内修复。

## 8. 零业务逻辑变更约束说明

本方案全部修改点的业务隔离性声明：

| 修改项 | 与业务逻辑的边界 |
|---|---|
| C1 waitress / C12 health / C11 上传目录 | 仅替换服务器容器与新增探活端点，未触碰任何 API 业务函数 |
| C2/C3 密钥注入 | 仅改变配置读取来源（默认值 → 强制环境变量），配置读取后所有下游逻辑不变 |
| C4 任务拆分 | 复用现有 jobs.run_loop 逻辑原样执行，仅改变"由谁调度"（进程内线程 → systemd timer） |
| C5 连接池 | 仅替换连接的获取/归还方式，事务边界（commit/rollback 时机）逐字保留，q1/qall/execute 及全部 SQL 零改动 |
| C6 直链收紧 | 删除的是"旁路匿名入口"，正路 /api/v1/files 鉴权下载逻辑不变 |
| C7 登录限流 | 仅在登录函数入口增加计数判断，登录成功/失败判定、token 签发、返回结构全部不变（仅新增一种 40001 频控消息，不改变既有场景行为） |
| C8/C9/C10 依赖与开关 | 配置文件与启动开关，无代码路径变化（seed 增加开关判断属环境分支非业务分支） |

**最终保障手段**：全部修改合入前执行 P0-3~P0-5（186 项 E2E/回归 + UI 24 步 + 文档边界校验），任何一项 FAIL 即视为引入业务回归，禁止合并。
